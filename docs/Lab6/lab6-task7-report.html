Token ERC-20, MetaMask e Interfacce: tutto spiegato semplice

Questo report raccoglie passo-passo tutto quello che hai costruito per il task di pagina 7 di Lab 6 - Manual.pdf: dalla creazione della tua criptovaluta UniToken (UNI) su Hardhat fino al collegamento con MetaMask e alla chiamata tra due smart contract diversi tramite ERC20Interface.

1. Cos'è un Token Non è una "moneta nel browser": è un contratto con un registro (balanceOf) che segna chi possiede quanto.
2. Cos'è MetaMask È una finestra visiva sulla blockchain: legge il contratto del token e ti mostra nome, simbolo e saldo.
3. Cos'è l'Interface È il "telecomando" (IERC20.sol): dichiara solo i nomi delle funzioni per far parlare due contratti.
4. Chi paga cosa Quando xzy chiama token.transfer(), il mittente è xzy stesso, non il tuo account!
L'idea dietro l'esercizio

0. Il senso generale: come lavorano insieme i pezzi

Immagina il tuo esercizio come un sistema con 4 attori molto facili da visualizzare nella vita reale:

1. MyToken = Il foglio Excel della banca

È uno smart contract che tiene una tabella con scritto: "Indirizzo A ha 700 UNI, Indirizzo B ha 200 UNI...". Quando sposti token, non spedisci file: aggiorni solo due numeri in questa tabella.

2. MetaMask = L'app della banca sul telefono

MetaMask non conserva i token dentro Chrome: chiede al contratto MyToken quanto vale balanceOf(tuoIndirizzo) e te lo stampa pulito sullo schermo.

3. IERC20.sol = Il telecomando universale

Contiene solo i tasti (le firme delle 5 funzioni: transfer, approve, getAllowance, minting, burning), senza nessuna riga di implementazione dentro.

4. xzy = Un distributore automatico di token

È un secondo contratto che usa il telecomando per comandare MyToken. Ma proprio come un distributore automatico, per poter dare token ai clienti devi prima caricarlo con un po' di UNI!

A. ERC-20-Token.sol — Il contratto del token (MyToken)

È il cuore della tua criptovaluta. Gestisce il registro dei saldi (balanceOf), le autorizzazioni di spesa (allowance), la creazione di nuovi token (minting) e la distruzione (burning).

  • name, symbol, decimals = 18, totalSupply: i metadati standard che MetaMask legge in automatico appena incolli l'indirizzo del contratto.
  • constructor(...): gira una sola volta al deploy. Salva te (msg.sender) come owner, moltiplica _initialSupply per 10**18 (perché Solidity non ha decimali) e ti assegna tutto il saldo iniziale.
  • transfer(to, value): controlla che to non sia 0x000... e che msg.sender abbia abbastanza token, poi sposta i numeri e lancia l'evento Transfer.
  • approve(spender, value) & getAllowance(from, spender): permettono di delegare un altro indirizzo a spendere fino a una certa soglia al posto tuo, e di leggere quel limite.
  • minting(...) & burning(...): riservati solo all'owner (require(msg.sender == owner && _initAdd == owner)): aumentano o diminuiscono la quantità totale in circolazione.
contracts/lab6/ERC-20-Token.sol 
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.28;

contract MyToken {
    string public name;
    string public symbol;
    uint8 public decimals = 18;
    uint256 public totalSupply;
    address public owner;

    mapping(address => uint256) public balanceOf;
    mapping(address => mapping(address => uint256)) public allowance;

    event Transfer(address indexed from, address indexed to, uint256 value);
    event Approval(address indexed owner, address indexed spender, uint256 value);

    constructor(string memory _name, string memory _symbol, uint256 _initialSupply) {
        owner = msg.sender;
        name = _name;
        symbol = _symbol;

        // Scala l'offerta iniziale con i 18 decimali standard ERC-20
        uint256 scaledSupply = _initialSupply * (10 ** uint256(decimals));
        totalSupply = scaledSupply;
        balanceOf[msg.sender] = scaledSupply;

        emit Transfer(address(0), msg.sender, scaledSupply);
    }

    function transfer(address to, uint256 value) public returns (bool) {
        require(to != address(0), "Invalid recipient");
        require(balanceOf[msg.sender] >= value, "Insufficient balance");

        balanceOf[msg.sender] -= value;
        balanceOf[to] += value;

        emit Transfer(msg.sender, to, value);
        return true;
    }

    function approve(address spender, uint256 value) public returns (bool) {
        require(spender != address(0), "Invalid spender");
        allowance[msg.sender][spender] = value;

        emit Approval(msg.sender, spender, value);
        return true;
    }

    function getAllowance(address from, address spender) public view returns (uint256) {
        return allowance[from][spender];
    }

    function minting(address _initAdd, address _toAdd, uint256 _mintAmount) public {
        require(msg.sender == owner && _initAdd == owner, "Only owner can mint");
        require(_toAdd != address(0), "Invalid recipient");

        totalSupply += _mintAmount;
        balanceOf[_toAdd] += _mintAmount;

        emit Transfer(address(0), _toAdd, _mintAmount);
    }

    function burning(address _initAdd, address _toAdd, uint256 _burAmount) public {
        require(msg.sender == owner && _initAdd == owner, "Only owner can burn");
        require(balanceOf[_toAdd] >= _burAmount, "Insufficient balance to burn");

        balanceOf[_toAdd] -= _burAmount;
        totalSupply -= _burAmount;

        emit Transfer(_toAdd, address(0), _burAmount);
    }
}

B. IERC20.sol — L'interfaccia (ERC20Interface)

Un'interface in Solidity non contiene variabili di stato né codice dentro { ... }: elenca soltanto le firme delle funzioni marcate external (obbligatorio nelle interfacce) per permettere a un contratto esterno di sapere come chiamare il token.

contracts/lab6/IERC20.sol 
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.28;

interface ERC20Interface {
    function transfer(address to, uint256 value) external;
    function approve(address spender, uint256 value) external;
    function getAllowance(address from, address spender) external view;
    function minting(address _initAdd, address _toAdd, uint _mintAmount) external;
    function burning(address _initAdd, address _toAdd, uint _burAmount) external;
}
Dettaglio curioso dal manuale: nel PDF la firma getAllowance(...) è scritta senza returns (uint256). Solidity la compila senza problemi; se un giorno volessi anche leggere quel valore da dentro un altro contratto, ti basterebbe aggiungere returns (uint256).

C. ERC20_InterfaceCall.sol — Il contratto chiamante (xzy)

Importa ./IERC20.sol, salva l'indirizzo del tuo token dentro il riferimento token = ERC20Interface(_tokenAddress) al momento del deploy, e offre la funzione sellToken(_to, _amount) che chiama token.transfer(_to, _amount).

contracts/lab6/ERC20_InterfaceCall.sol 
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.28;

import "./IERC20.sol";

contract xzy {
    ERC20Interface token;
    address public owner = msg.sender;

    constructor(address _tokenAddress) {
        token = ERC20Interface(_tokenAddress);
    }

    function sellToken(address _to, uint _amount) public {
        token.transfer(_to, _amount);
    }
}

Fase 3 — Deploy del Token e importazione in MetaMask

Passo 5 ethers.deployContract("MyToken", ["UniToken", "UNI", 1000])
Dalla console Hardhat (npm run console) hai pubblicato MyToken sulla rete locale creando 1,000 UNI e assegnandoli automaticamente all'Account #0 (owner).
Passo 6 MetaMask → Import tokens → Custom token
Incollando tokenAddress sulla rete Hardhat Local, MetaMask ha interrogato il tuo contratto, letto automaticamente simbolo UNI e decimali 18, e ti ha mostrato 1,000 UNI nel wallet.

Fase 4 — Deploy di xzy e trasferimento tramite Interface

Passo 7 ethers.deployContract("xzy", [tokenAddress])
Hai deployato il secondo contratto xzy collegandolo all'indirizzo di MyToken.
Passo 8 token.transfer(callerAddress, 300 UNI) → caller.sellToken(receiver, 100 UNI)
Prima hai rifornito xzy con 300 UNI (così su MetaMask il tuo saldo è sceso a 700 UNI), poi hai chiamato sellToken su xzy che, usando ERC20Interface, ha trasferito 100 UNI dal saldo di xzy a receiver (Account #1).
Perché il Passo 8 era fondamentale?
Dentro xzy.sellToken(), l'istruzione token.transfer(_to, _amount) parte dal contratto xzy, non dal tuo account personale. Quindi dentro MyToken.transfer() la variabile msg.sender vale callerAddress (l'indirizzo di xzy)! Senza quei 300 UNI caricati prima su xzy, la chiamata sarebbe fallita con "Insufficient balance".

5. I 3 concetti chiave + Mini-Quiz di ripasso

1. ETH vs Token ERC-20

I 10,000 ETH sono la moneta nativa della rete e servono a pagare il gas delle transazioni. I 1,000 UNI sono invece numeri salvati nella memoria del tuo contratto MyToken.

2. Perché 18 decimali

Solidity non ha i numeri con la virgola (float). Quindi 1 UNI viene salvato come 1018 unità minime: si usa parseUnits(..., 18) per inviare e formatUnits(..., 18) per leggere.

3. Cambio di msg.sender

Se tu chiami xzy e xzy chiama MyToken, dentro MyToken il valore di msg.sender è l'indirizzo di xzy, non il tuo!
